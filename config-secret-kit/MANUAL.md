# config-secret 하네스 매뉴얼 (처음 보는 사람용)

> 모르는 용어가 나오면 `core/GLOSSARY.md`(용어풀이)를 함께 보세요.
> 이 문서 하나만 읽어도 이 하네스가 왜 있고 무엇을 하는지 알 수 있게 썼습니다.

---

## 1. 이 하네스가 왜 있나 (비유로)

외부망(개발하는 곳)과 내부망(은행 안)은 분리돼 있습니다.
그래서 **개발할 때는 진짜 서버 주소·접속코드·비밀번호를 알 수도, 써서도 안 됩니다.**

비유하자면, **편지 봉투에 받는 주소를 미리 쓰지 않고 `[받는 주소]` 라고만 적어 두는 것**과 같습니다.
편지 내용(코드)은 다 써 두고, 봉투의 주소 칸은 **빈 자리**로 비워 둡니다.
나중에 내부망(우체국)에 들어가서 그 빈 자리에 진짜 주소만 도장처럼 찍습니다.

이 하네스는 그 **"빈 자리 ↔ 진짜 값"** 의 연결을 안전하게 관리합니다.

- 빈 자리 표기: `${MESSENGER_HOST}` 처럼 대문자_밑줄 이름
- 빈 자리 목록: `binding.yaml` (어떤 빈 자리가 있는지, 진짜 값은 내부망 어디서 오는지)

---

## 2. 안 쓰면 무슨 일이 나나 (실패 사례)

빈 자리 규칙 없이 개발하면 흔히 이렇게 사고가 납니다.

- 개발자가 편하게 코드에 `HOST = "http://10.20.30.40/..."` 라고 **진짜 주소를 박아** 둠
  → 그 코드가 외부망 저장소·깃 기록에 남아 **내부망 주소가 외부로 유출**됩니다.
- 비밀번호·접속코드를 코드에 박아 두고 깜빡 잊음 → 보안 사고.
- 개발/운영 주소가 코드마다 흩어져 있어서, 내부망 반입할 때 **코드를 여기저기 고쳐야** 함
  → 고치다 실수, 환경마다 동작이 달라짐.

이 하네스의 게이트(`check-no-hardcoded-values`)는 위 같은 **실제 값 박힘을 자동으로 잡아**
반입 자체를 막습니다. (이 게이트는 예외 승인으로도 우회 불가 — 보안 핵심이라서요)

## 3. 실제 예시로 따라가기 (메신저 사례 한 바퀴)

사내 쪽지(messenger) 발송 기능을 외부망에서 개발한다고 합시다.

**(1) 솔루션 카드에서 빈 자리가 어디인지 확인**
`internal-solution-kit/solution-card.messenger.yaml` 을 보면
HOST·SRV_CODE 는 "내부망에서 주입한다"고 비워 둔 상태입니다. → 이게 빈 자리 후보.

**(2) 빈 자리 목록 작성** — `binding.messenger.example.yaml` 참고

| 빈 자리 이름 | 종류 | 사는 곳 | 진짜 값은? |
|---|---|---|---|
| `MESSENGER_HOST` | secret | internal-only | 내부망 환경설정에서 주입 |
| `MESSENGER_SRV_CODE` | secret | internal-only | 담당자 발급, 비밀 저장소에서 주입 |
| `MESSENGER_PATH` | config | external-ok | 기본값 `/HMemoServiceUtf8` |
| `MESSENGER_ENCODING` | config | external-ok | 기본값 `UTF-8` |
| `MESSENGER_TIMEOUT_MS` | config | external-ok | 기본값 `3000` |

- **secret**(민감) = 진짜 값을 외부망에 절대 안 적음. 빈 자리로만.
- **config**(안 민감) = 기본값을 외부망에 적어도 됨 (타임아웃·인코딩 등).

**(3) 코드는 빈 자리로만 작성**
```python
HOST = os.environ["MESSENGER_HOST"]   # 진짜 주소 X, 빈 자리만
url  = f"{HOST}{PATH}"
```

**(4) 게이트로 자기검사**
```bash
gates/check-bindings-complete.sh   binding.messenger.example.yaml
gates/check-no-hardcoded-values.sh ./src       # 코드 폴더를 훑어 실제 값 박힘 검사
```

**(5) 내부망 반입 시**
빈 자리에 진짜 값만 주입 → **코드는 한 줄도 안 고침.** 끝.

## 4. 내가 직접 할 일 vs 자동으로 되는 일

| 구분 | 누가 | 무엇을 |
|---|---|---|
| 🟡 직접 | 당신/담당자 | `binding.yaml` 에 빈 자리 목록 적기 (이름·종류·설명) |
| 🟡 직접 | 개발자 | 코드에 진짜 값 대신 `${...}` 빈 자리 쓰기 |
| 🔴 내부망 | 내부 담당자 | 반입 시 빈 자리에 진짜 값 주입 (외부망에선 안 함) |
| 🟢 자동 | 게이트 | 실제 값 박힘·규칙 위반 자동 검사 |
| 🟢 자동 | 스키마 | binding.yaml 형식 자동 검사 |

> 핵심: **당신은 "빈 자리 목록"만 만들면 됩니다.** 진짜 값을 채우는 건 내부망 몫이고,
> 잘못 박힌 게 있으면 게이트가 알아서 잡습니다.

## 5. 자주 막히는 곳 (FAQ)

**Q. config 와 secret 을 어떻게 구분하나요?**
A. "이 값이 밖에 알려지면 곤란한가?"로 판단합니다. HOST·접속코드·비밀번호·토큰·인증서 →
secret. 타임아웃·재시도횟수·인코딩 같은 동작 설정 → config.

**Q. secret 에 기본값(default)을 넣으면 왜 안 되나요?**
A. 기본값 자리에 실수로 진짜 값을 적게 되는 사고가 가장 흔합니다. 그래서 secret 은
기본값을 아예 못 넣게 막아 뒀습니다(게이트가 잡음).

**Q. `${MESSENGER_HOST}` 같은 빈 자리는 게이트가 실제 주소로 오해하지 않나요?**
A. 아니요. 게이트는 `${...}` 빈 자리를 먼저 가린 뒤 검사하므로, 빈 자리는 통과시키고
진짜로 박힌 값만 잡습니다.

**Q. pyyaml 이 없다고 나옵니다.**
A. `pip install pyyaml` 후 다시 실행하세요. (게이트는 python3 + pyyaml 로 동작)

**Q. 빈 자리 이름 규칙은 어디서 바꾸나요?**
A. `policy.yaml` 의 `placeholder` 와 `forbidden_real_value_patterns` 에서 조정합니다.
