# 데이터 표준 품질 하네스 — 설계 (코딩 전, 설계 단계)

> 목적: "개발/배포 전에 데이터 품질 기준 위반을 자동으로 차단"하되,
>       개발자 품을 거의 들이지 않고(메타테이블 자동생성), 표준 테이블에만 적용.
> 상태: 설계 확정용 초안. 코딩은 승인 후.

---

## 1. 한 줄 요약

개발자가 **테이블명만** 대면 → 하네스가 **메타테이블에서 그 테이블의 규칙을 읽어** →
검사를 **자동 생성·실행** → 위반 시 **차단(표준 테이블)** 또는 **건너뜀(비표준)**.
개발자는 규칙을 한 줄도 안 쓴다.

## 2. 설계 원칙 (= "품이 적다"의 근거)

1. **단일 기준(Single Source of Truth) = 메타테이블.** 규칙을 코드/문서에 흩지 않는다.
2. **검사 자동생성.** 메타테이블의 컬럼(타입·NOT NULL여부·유효값·표준적용여부 등)에서
   검사를 만들어낸다 → 테이블당 한계비용 ≈ 0.
3. **표준 테이블만 강제.** `표준적용여부=1` 인 테이블만 값 검사. `0`이면 건너뜀.
4. **사람과 역할 분담.** 기계는 반복·기계적 규칙을 전수로, 사람은 의미·판단에 집중.
5. **점진 도입.** 처음엔 핵심 검사만 차단(blocking), 나머지는 경고(warning)로 시작.

## 3. 아키텍처 (흐름)

```
[개발자/CI] "TDDPSX901 검사"
      │
      ▼
① 메타테이블 조회 ──► 그 테이블의 행들(컬럼별 규칙) 로드
      │                 (스키마명, 정의, 표준적용여부, 타입, NOT NULL, 유효값 …)
      ▼
② 표준 판정 (표준적용여부 0/1)
      │   0 → 값검사 건너뜀(통과) / 1 → 계속
      ▼
③ 검사 자동생성 (메타 → 규칙)
      │   타입 date8 → 날짜검사,  유효값 목록 → 도메인검사,  NOT NULL → 결측검사 …
      ▼
④ 대상 데이터에 규칙 실행 (개발 산출물 / 적재 샘플)
      │
      ▼
⑤ 결과: 위반 0 → 통과(exit 0) / 위반 有 → 실패(exit 1, 위반목록)
```

## 4. 어디서 도는가 (실행 위치) — 개발 중 수작업이 아님

- 개발자 로컬: 명령 1회(선택)
- **CI / 배포 전 게이트(주력)**: PR·배포 파이프라인에서 자동. 위반 시 머지/배포 차단.
- 적재 후 배치(선택): 운영 데이터에 같은 규칙 재실행(실데이터 검증).
- → "개발하면서 매번 손으로"가 아니라 **파이프라인이 알아서** 돈다.

## 5. 검사 카탈로그 (차원별) — 무엇이 구동하나

| 차원 | 검사 | 구동하는 메타 컬럼 | 1차 도입 |
|---|---|---|---|
| 완전성 | NOT NULL인데 결측 | not_null 여부 | ✅ 차단 |
| 유효성(타입) | date8 → 유효 YYYYMMDD | data_type | ✅ 차단 |
| 유효성(도메인) | 유효식별자 목록 밖 값(예 0) | valid_values | ✅ 차단 |
| 유효성(길이/범위) | 자릿수·금액음수·비율범위 | length / min / max | ▶ 2차 |
| 유일성 | PK·업무키 중복 | pk 여부 | ▶ 2차 |
| 참조무결성 | 코드가 마스터에 존재 | fk_ref | ▶ 3차 |
| 일관성(컬럼간) | 해지일≥개설일 등 | rule 식 | ▶ 3차 |
| 마스킹/프라이버시 | 개인정보 평문 금지 | masking 대상여부 | ▶ 2차(정책따라) |
| 적시성 | 미래일자·과도한 과거 | (date8 + 기준) | ▶ 선택 |

→ **메타테이블이 어떤 플래그를 들고 있느냐가 곧 가능한 검사 범위.**
   (메타 스키마 설계가 검사 설계다)

## 6. 차단 vs 경고 (노이즈 관리)

- 1차: 완전성·타입·도메인만 **차단(fail)**. 나머지는 **경고(report)** 로 시작.
- 오탐이 많으면 신뢰를 잃으므로, 확실한 것만 막고 점진 확대.

## 7. 사람(품질검증 업무)과의 분담

- 기계: 기계적·반복·전수 검사를 빌드마다 무료로.
- 사람: 업무의미 판단, 신규 규칙 발굴, 예외 협의, 대사 결과 해석.
- 효과: 단순오류를 사람이 매번 찾던 부담 ↓, 판단이 필요한 곳에 집중 ↑.

## 8. 비용/노력 분석

| 항목 | 비용 | 시점 |
|---|---|---|
| 하네스 구축 | 1회 | 초기 |
| 메타테이블에 플래그 채우기 | 1회(+신규시 갱신) | 초기/운영 |
| 테이블당 검사 작성 | **0 (자동)** | — |
| 테이블당 실행 | 자동(CI) | 매 빌드 |

→ 선투자 후 **확장 비용 거의 0**. 이게 "품 많이 들지 않냐"의 답.

## 9. 메타테이블에 필요한(있으면 좋은) 컬럼 — 설계 요청

검사 범위를 키우려면 메타테이블(익명화본)에 아래가 있는지 확인 필요:
`테이블명 · 스키마명 · 정의 · 표준적용여부(0/1) · 컬럼명 · 컬럼정의 · 데이터타입 ·
 NOT NULL여부 · 최대길이 · 유효값목록 · PK여부 · 마스킹대상여부 · FK참조`

## 10. 미결정 / 다음 단계

- [ ] 1차 차단 검사 범위 확정 (완전성·타입·도메인 제안)
