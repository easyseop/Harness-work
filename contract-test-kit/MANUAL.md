## 1. 이 하네스가 왜 있나 (비유로)

internal-solution 하네스에서 "메뉴판(계약)"을 적었습니다.
그런데 **메뉴판만 있고 요리가 메뉴판대로 나오는지 확인 안 하면** 소용없습니다.

이 하네스는 **메뉴판과 실제 요리가 일치하는지 시식하는 단계**입니다.
"이 입력을 주면 이 결과(또는 이 오류코드)가 나와야 한다"는 테스트를 계약에서 뽑아 내고,
코드가 그대로 동작하는지 **대역(Mock)으로** 검사합니다.

실제 내부 시스템에 연결하지 않고, 외부망에서 가짜 응답으로 검증합니다.

---

## 2. 안 쓰면 무슨 일이 나나 (실패 사례)

- 코드는 잘 돌아가는 줄 알았는데, 계약에 적힌 **오류코드 처리를 빠뜨림**
  → 내부망에서 실제 연결하니 못 보던 오류에 프로그램이 멈춤.
- 필수 입력을 안 보냈는데도 코드가 그냥 진행 → 내부 시스템이 거절 → 장애.
- 계약은 바뀌었는데 코드는 옛날 그대로 → 반입 후에야 발견.

이 하네스의 게이트는 "계약의 모든 오류코드·정상·필수누락 경로에 테스트가 있는지" 검사해서,
**빠진 처리를 반입 전에** 잡습니다.

## 3. 실제 예시로 따라가기 (메신저 사례)

`test-spec.messenger.example.yaml` 은 `solution-card.messenger.yaml` 의 약속을
테스트 케이스 10개로 옮긴 것입니다.

| 케이스 종류 | 예 | 기대 결과 |
|---|---|---|
| 정상(happy) | 정상 입력 | `0` (OK) |
| 필수누락 | SRV_CODE 없음 | `33` |
| 필수누락 | RECIPIENT 없음 | `34` |
| 오류 | 미등록 코드 | `38` |
| 오류 | 발신 IP 미등록 | `48` |
| 오류 | 기타 | `64` |

```bash
gates/check-contract-coverage.sh \
    test-spec.messenger.example.yaml \
    ../internal-solution-kit/solution-card.messenger.yaml
```

게이트는 카드의 **오류코드를 하나라도 테스트가 안 덮으면** 실패시킵니다.
(예: `64` 케이스를 지우면 "테스트가 빠진 오류코드: ['64']" 로 막힘)

> 입력값은 전부 가짜(`z000001` 같은 더미 직원번호)입니다. 실제 직원번호·고객정보 금지.

## 4. 내가 직접 할 일 vs 자동으로 되는 일

| 구분 | 누가 | 무엇을 |
|---|---|---|
| 🟡 직접 | 개발자 | 계약을 보고 `test-spec.yaml` 에 케이스 적기 |
| 🟡 직접 | 개발자 | 코드를 대역(Mock)에 맞춰 테스트 돌리기 |
| 🟢 자동 | 게이트 | 오류코드·정상·누락 경로를 다 덮었는지 검사 |
| 🟢 자동 | 게이트 | 테스트 데이터에 실제 민감정보 섞였는지 검사 |

> 핵심: 당신은 **"계약을 테스트 케이스로 옮기는 일"** 을 합니다.
> 빠진 경로가 있으면 게이트가 알려 줍니다.

## 5. 자주 막히는 곳 (FAQ)

**Q. 실제 내부 시스템에 연결해서 테스트하면 안 되나요?**
A. 외부망에서는 안 됩니다(`external_tests_must_use_mock`). 대역(Mock)으로만 합니다.
실제 연결 확인은 내부망 reproduce 단계(adapter-smoke-test)에서 합니다.

**Q. 케이스를 다 적기 너무 많아요.**
A. 최소한 "정상 1개 + 필수누락 + 모든 오류코드"는 있어야 통과합니다.
오류코드가 곧 케이스 수라서, 카드의 errors 목록을 그대로 옮기면 됩니다.

**Q. 어떤 게 happy / error / missing-field 인가요?**
A. happy=정상 성공, error=시스템이 오류코드를 주는 경우, missing-field=필수 입력을 빠뜨린 경우.

**Q. pyyaml 오류가 납니다.**
A. `pip install pyyaml` 후 다시 실행하세요.
